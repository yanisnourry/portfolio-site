Vectorized Backtester

An evaluation engine, not an alpha search. It replays a strategy over historical candles and reports what would have happened, honestly: no look-ahead, transaction costs on by default, metrics annualized for the bar size. A small service re-runs it every hour on fresh data from my market data pipeline.

Live backtest

Simulation, not a trading signal. This is a plain SMA crossover used to exercise the engine end to end on real, refreshed data. It is not a recommendation, a forecast, or a record of real performance. The strategy is not meant to make money, and the page shows whatever it does.

Every hour, the service pulls the last 30 days of BTCUSDT 1h candles from the pipeline's REST API, runs the engine, and keeps the result in memory. This page asks it for the result on each request, server-side: the service has no public address and is only reachable from inside the cluster. If it doesn't answer within two seconds, you get a labelled static example instead of an error.

One demo strategy, on purpose

The only strategy is an SMA crossover: long while the 10-bar average is above the 30-bar one, short while it is below, flat until both averages exist. There is no parameter search and no optimisation. The crossover is a test vehicle: simple enough that any oddity in the results points at the engine, not the strategy. The value is in the measurement.

No look-ahead

The position held through bar t is the signal decided at the close of t−1: position = signal.shift(1). It happens in exactly one place, so the guarantee can be audited, and a test truncates the input mid-series to check that no past value changes.

Costs on by default

Every change of position pays 10 bps of fees and 5 bps of slippage per unit traded. Holding is free, an entry pays once, a long↔short flip pays twice. These rates are conservative placeholders, not calibrated to a venue.

Correct annualization

A mean scales with time, a standard deviation with its square root, and both depend on the bar size. The number of bars per year is always passed in by the caller (8,760 for hourly bars), never a hard-coded 252.

Bad data fails loudly

The data loader refuses a series with a missing candle instead of forward-filling it: a silently patched gap would distort every return after it. A hole in the data means a failed refresh, not a wrong curve.

Tests that can't agree with a bug

The engine has 65 tests, including a dedicated suite that checks its honesty claims end to end, each written so that it can't pass by re-running the code it tests:

  • An always-long strategy with zero costs must match buy-and-hold exactly. The reference is close / close[0], computed independently of the engine.
  • A flat signal must give a flat equity curve, on prices that do move and with costs on.
  • Truncating the input must leave every earlier position, cost and equity value bit-for-bit identical.

The service adds 21 tests of its own, with the pipeline mocked. Both repositories run their tests in CI on every push.

Service design

  • Stateless, nothing to leak. The latest result lives in memory: no database, no credentials. A restart just recomputes it.
  • Two read-only routes, internal only. /results and /health, behind a ClusterIP Service. FastAPI's /docs is disabled.
  • No current position exposed. The result carries metrics and the equity curve, never the position held now: that is the one field someone could take for a live signal.
  • Failures degrade, never crash. A failed refresh keeps the previous result and marks it stale after two missed hours. The health check stays green, so a pipeline outage doesn't send the pod into a restart loop.
  • The engine is a dependency, not a copy. The service installs it from GitHub, pinned by commit sha.

Known limitations

  • A single demo strategy and a single market (BTCUSDT, 1h).
  • A gap in the pipeline's data inside the 30-day window blocks refreshes until the pipeline backfills it; the result shows as delayed meanwhile.
  • Single replica by design: the state is in memory, so two replicas would serve two different results.
  • No history of past runs: the page only shows the latest one.
