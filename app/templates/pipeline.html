Market Data Pipeline

Fetches OHLCV candles from Binance, validates them, stores them in TimescaleDB and serves them over a FastAPI REST and WebSocket API, with a Streamlit dashboard on top. It runs around the clock on my Kubernetes cluster and is the data source for the backtester's live demo.

In production: 3 symbols × 5 timeframes, refreshed continuously.

Data flow

  1. Binance/api/v3/klines
  2. Fetcherasync, paginated
  3. Normalizer→ typed Candle
  4. Validatorflags anomalies
  5. Repositoryupsert
  6. TimescaleDB + Redishistory + last price
  7. FastAPIREST + WebSocket

One scheduled job per timeframe (1m, 5m, 15m, 1h, 1d) for BTCUSDT, ETHUSDT and BTCUSDC. Jobs are independent: a failure in the 1m job doesn't touch the 1h one.

Design decisions

Idempotent, self-correcting writes

Every write is an upsert on (timestamp, symbol, exchange, timeframe). A row is only rewritten when a price or the volume actually differs (IS DISTINCT FROM), so re-running a range is a no-op, and the still-open candle Binance returns gets its final values on the next fetch.

Flag bad data, never drop it

Gaps, price jumps over 20%, volume spikes over 10× the 24-candle mean and physically impossible candles are flagged, not removed. Whether to exclude them is the consumer's decision. The counts are exposed on /health/data-quality.

Resume, don't restart

Each job resumes from the latest stored candle. An empty series is backfilled over a horizon sized to about 10,000 candles (7 days of 1m, a year of 1h, five years of 1d), and that same horizon bounds how far a job reaches back after a long outage.

Exact numbers, explicit time

Prices are NUMERIC(20, 8) in the database and Decimal in Python, never floats. Timestamps are TIMESTAMPTZ, always UTC, so a server locale change can't shift the data.

Async end to end, with limits

aiohttp, asyncpg and redis.asyncio keep the event loop free. Binance calls are capped at 10 concurrent requests, with exponential backoff (1s, 2s, 4s) on failure. WebSocket connections are capped too.

Fail fast at startup

The API checks its database and Redis before accepting traffic. If either is missing, the process exits with a clear error instead of serving in a half-working state.

In production

  • Packaged as a Helm chart in a separate infrastructure repository: API, dashboard, Redis, TimescaleDB and a one-off Job that creates the schema.
  • State lives in one place. TimescaleDB runs as a StatefulSet on a persistent volume; everything else can be deleted and recreated.
  • Image pinned by commit sha, built and pushed to GHCR by CI, never latest.
  • No credentials in the repositories. They are public; the database password lives in a Kubernetes Secret created by hand.
  • Rate-limited at the edge. The public API and dashboard go through Traefik middlewares that cap both the request rate and the number of concurrent requests per client IP, read from Cloudflare's Cf-Connecting-IP header.

Tests and CI

53 tests covering the fetcher, normaliser, validator, repository, scheduler jobs, API and WebSocket. CI runs them against real TimescaleDB and Redis service containers, then builds the image and pushes it to GHCR.

Known limitations

  • Anomaly flags are set on first insert and not recomputed when a later fetch corrects a candle: re-validating needs the neighbouring candles, which the upsert doesn't have. An accepted trade-off that keeps ingestion and validation decoupled.
  • A gap older than the backfill horizon is logged, not recovered.
  • A single source (Binance spot).
