k3s · Helm · Traefik · Cloudflare Tunnel

Infrastructure

Everything on this site runs on one mini PC at home: a single-node k3s cluster that the internet can only reach through an outbound Cloudflare Tunnel. No port is open to the internet, on the machine or the router. The Helm charts and manifests are public.

How a request gets here

  1. VisitorHTTPS
  2. CloudflareDNS, TLS
  3. Tunneloutbound, 2 connectors
  4. Traefikrate limits
  5. Ingressroutes by host
  6. Service → PodClusterIP

cloudflared runs inside the cluster as two replicas of the same tunnel. Each one dials out to Cloudflare, so nothing listens for inbound connections and the home IP address never appears in DNS. Cloudflare terminates TLS and forwards each public hostname to Traefik, which routes on the Host header. Two connectors mean a rolling update or a crashed pod doesn't cut public traffic. The tunnel's routing is a versioned ConfigMap, not settings in a dashboard.

Locking down a server on a home connection

Firewall, IPv6 included

The machine has a global IPv6 address, and IPv6 means no NAT to hide behind. ufw covers IPv4 and IPv6, the router's IPv6 firewall is on, and an external IPv6 scan confirmed that SSH (22), the Kubernetes API (6443), the kubelet (10250), 80 and 443 are all unreachable from the internet.

Rate limits per real visitor

Behind the tunnel every request comes from cloudflared, so a naive limit would give all visitors one shared quota. Traefik middlewares key the request rate and the concurrent-request cap on Cloudflare's Cf-Connecting-IP header instead.

No secret in a public repo

The repositories are public. The database password and the tunnel credentials live in Kubernetes Secrets created by hand. Secret manifests and credential files are git-ignored, and only an example file is committed.

Least privilege in the pods

The tunnel and the backtester run as a non-root user, with a read-only root filesystem, every Linux capability dropped and privilege escalation off. The backtester also gets the default seccomp profile and no service account token. Databases and internal services are ClusterIP only.

Patched without waiting for me

The host runs Ubuntu Server with unattended-upgrades: a machine exposed around the clock has to stay patched even when nobody is looking at it.

Images pinned by commit sha

Application images are pinned to the commit sha CI built, never latest, so what runs is exactly what was reviewed. TimescaleDB and cloudflared are pinned to an exact release.

From a commit to the cluster

  1. git pushapplication repo
  2. CI testsGitHub Actions
  3. Build + pushGHCR, tagged by sha
  4. Bump the shacommit in infra
  5. helm upgradeon the cluster

Each application builds its own image. The infrastructure repository decides which sha runs, in one place per chart, so a deployment is a reviewed commit and a rollback is the previous sha. The last step is still manual: see the limitations below.

Kubernetes choices

  • One replica where state lives in the process. The pipeline API runs the ingestion scheduler and the backtester keeps its result in memory. Both are pinned to one replica with a Recreate strategy, so a rollout never runs two copies side by side.
  • Liveness never depends on a dependency. A database outage should make a pod not ready, not restart it in a loop: liveness checks the process itself, readiness checks the dependencies.
  • State in exactly one place. TimescaleDB is a StatefulSet on a persistent volume, with guaranteed CPU and memory. Everything else can be deleted and recreated.
  • No start order, so wait explicitly. Kubernetes has no depends_on: the API and the schema Job wait for the database with an init container, and the schema Job is an idempotent Helm hook.
  • Config changes roll the pod. Environment variables are only read at start, so the backtester chart hashes its ConfigMap into a pod annotation: changing the config triggers a rollout on its own.

Known limitations

  • One node. A hardware failure or a power cut takes everything down. No high availability, by design and by budget.
  • No off-machine database backup yet. Recent history can be re-ingested from Binance, but that is partial recovery, not a backup.
  • No monitoring stack. No Prometheus or alerting yet: an outage is noticed, not reported.
  • Deploys are run by hand. helm upgrade from a reviewed commit, not GitOps. No Terraform either: there is no cloud resource to provision.
